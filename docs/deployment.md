# Deployment

## Run locally

Requirements: Node.js 20.19+ (22 LTS recommended), npm 10+, and MongoDB (local install or an Atlas cluster).

1. Install dependencies from the repository root:

   ```bash
   npm install
   ```

2. Create the server environment file and fill in the values:

   ```bash
   cp server/.env.example server/.env
   ```

   - `JWT_SECRET` must be at least 32 characters. Generate one with
     `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`.
   - Leave `MONGODB_URI` empty to use a local MongoDB at `mongodb://127.0.0.1:27017/estate-assist`.
   - With `LLM_PROVIDER=mock` the assistant runs without an API key.

3. Load the demo data (wipes the database in `MONGODB_URI` first):

   ```bash
   npm run seed
   ```

   It creates both projects, five staff accounts, about 60 leads with chats, three weeks of slots,
   visits and source spend. The same command always produces the same data. Every staff account uses
   the password in `SEED_PASSWORD` (default `Demo@12345`). With `NODE_ENV=production` it refuses to
   run; use `node src/seed/index.js --force` inside `server/` if you really mean it.

4. Start the API and the web app together:

   ```bash
   npm run dev
   ```

   - Web app: http://localhost:5173
   - API health: http://localhost:4000/api/health (returns `database: "up"` when MongoDB is reachable)

   The web app proxies `/api` to the API in development, so `client/.env.local` is not needed locally.

## External services

### MongoDB Atlas

1. Create a free M0 cluster at https://cloud.mongodb.com.
2. Database Access: add a database user with a generated password.
3. Network Access: allow the API host. For local testing add your current IP.
4. Connect, Drivers: copy the `mongodb+srv://` connection string, insert the password and add the
   database name `estate-assist` before the `?`.
5. Put it in `MONGODB_URI`. Atlas clusters are replica sets, which the booking transactions need.

### Groq

1. Create an API key at https://console.groq.com/keys.
2. Set `LLM_PROVIDER=groq` and `GROQ_API_KEY`. `GROQ_MODEL` defaults to `openai/gpt-oss-120b`, the strongest tool-calling model on the free plan (Llama 3.3 70B is Enterprise-only now).
   The free plan allows about 8,000 tokens a minute per model, roughly two or three buyer
   messages. When the main model is rate limited the API moves to `GROQ_FALLBACK_MODEL`
   (default `openai/gpt-oss-20b`, which has its own limit); if both are busy the buyer is handed
   to a sales executive. Groq's paid Developer tier removes the limit for real traffic.

## Deploy

The API runs on Render, the web app on Vercel and the data on MongoDB Atlas. Every secret is typed into
a dashboard; the repository only holds variable names (`render.yaml`, `.env.example` files).

Live URLs:

- Web app: https://estate-assist.vercel.app (staff console at `/staff/login`)
- API health: https://estate-assist-api.onrender.com/api/health

### 1. Atlas: a database for the live app

1. Database Access: add a user only for the live app (for example `estate-assist-live`) with a
   generated password and the built-in role `readWrite` on the database `estate-assist-live`.
2. Network Access: add `0.0.0.0/0`. Render free instances have no fixed outbound IP, so the strong
   password is the protection. Keep your own IP entry for seeding from your machine.
3. Build the connection string with the database name before the `?`:
   `mongodb+srv://estate-assist-live:<password>@<cluster>.mongodb.net/estate-assist-live?retryWrites=true&w=majority`

Using a separate database keeps local development from changing the live demo data.

### 2. Render: the API

1. New, Blueprint, pick this GitHub repository. Render reads `render.yaml` and creates
   `estate-assist-api` (Node 22, Singapore region, health check `/api/health`).
2. It asks for the `sync: false` values:
   - `MONGODB_URI`: the connection string from step 1.
   - `GROQ_API_KEY`: the Groq key. Without one, change `LLM_PROVIDER` to `mock` in Environment.
   - `CLIENT_ORIGIN`: leave a placeholder such as `https://example.com` for now; it is set in step 4.
3. `JWT_SECRET` and `INGEST_API_KEY` are generated by Render. Read `INGEST_API_KEY` from the
   Environment tab when a lead source needs it.
4. After the first deploy, `https://<render-service>.onrender.com/api/health` should return
   `{"status":"ok","database":"up"}`. If the deploy fails, the log names the missing variable.

### 3. Vercel: the web app

1. Add New, Project, import this GitHub repository.
2. Root Directory: `client`. The framework is detected as Vite (`client/vercel.json` adds the SPA
   rewrite, security headers and long caching for hashed assets).
3. Environment Variables: `VITE_API_URL` = `https://<render-service>.onrender.com` (no trailing
   slash). Vite bakes it in at build time, so redeploy after changing it.
4. Deploy and note the production URL.

### 4. Connect the two

In Render, Environment, set `CLIENT_ORIGIN` to the exact Vercel production URL, for example
`https://estate-assist.vercel.app` (no trailing slash; separate several with commas). Render restarts
the API. Any other website gets `403` from the API.

### 5. Load the demo data

Render's free plan has no shell, so seed from your machine against the live database. From
`server/`, with the live connection string only in this one command:

```bash
MONGODB_URI="<live connection string>" npm run seed
```

The local `.env` stays untouched, and the command is not saved anywhere in the repository. Staff log in
with `Demo@12345` unless `SEED_PASSWORD` was set for the command.

### 6. Smoke test on the live app

On a laptop and on a phone (or a 375px-wide browser window):

1. Open the web app. The first load after idle can take up to a minute while Render wakes the API;
   the page sends a wake-up ping on load.
2. Chat: start as a buyer, ask about price and possession for a project, pick a free slot and confirm
   the visit. Ask for a call back or to talk to a person to trigger the handoff.
3. Staff: log in as `meera.desai@example.com`. The new lead shows the visit, the handoff summary and
   the assigned executive. Reply as staff from the lead page.
4. Dashboard: the source table counts the new lead and visit.
5. Log in as `ravi.mehta@example.com` and confirm only his own leads are visible.

### Free-tier behaviour

- Render free instances sleep after 15 minutes without traffic. A free uptime monitor (for example
  UptimeRobot or cron-job.org) calling `/api/health` every 10 minutes keeps the API awake, so reminders
  go out on time. One always-on service fits within Render's free monthly hours.
- Atlas M0 has 512 MB of storage, far more than the demo data needs.

## Useful scripts

| Script           | What it does                                   |
| ---------------- | ---------------------------------------------- |
| `npm run dev`    | API and web app with live reload               |
| `npm run seed`   | Replace the database contents with demo data   |
| `npm test`       | API tests against an in-memory MongoDB         |
| `npm run lint`   | ESLint across server and client                |
| `npm run format` | Prettier write                                 |
| `npm run check`  | Lint, format check, tests and production build |

Tests never touch the configured database. They start a throwaway in-memory MongoDB replica set; the
first run downloads the MongoDB binary (about 100 MB) and caches it.

## Environment variables (names only)

Server (`server/.env`): `NODE_ENV`, `PORT`, `MONGODB_URI`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `CLIENT_ORIGIN` (comma-separated CORS allowlist, e.g. the Vercel URL), `LLM_PROVIDER`, `GROQ_API_KEY`, `GROQ_MODEL`, `GROQ_FALLBACK_MODEL`, `INGEST_API_KEY`, `JOBS_ENABLED`, `SEED_PASSWORD`.

Visit reminders run inside the API process every minute (`JOBS_ENABLED=true`). They are idempotent, so
running more than one instance is safe. On a free host that sleeps when idle, reminders that came due
during the sleep go out when the API wakes, and a reminder is never sent after the visit has started.

Client (`client/.env.local`, only when the API is on another origin): `VITE_API_URL`.
